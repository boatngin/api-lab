## Defect report
- Title: Defect 1, excluding all three tools makes `POST /api/pizza` crash with 500 and an empty body
- Request: `POST https://quickpizza.grafana.com/api/pizza` with header `Authorization: token <token of a logged-in user>` and body `{"excludedTools": ["Knife", "Pizza cutter", "Scissors"]}` (`curl -i -H "@auth.txt" -d "@all_tools.json" https://quickpizza.grafana.com/api/pizza`)
- Expected result: No pizza can be cut without a tool, so the API refuses the request with status 400 and a JSON error message, for example `{"error": "no pizza matches the restrictions"}`.
- Actual result: Status `HTTP/2 500`, `content-length: 0`, no body at all. Covered by `test_excluded_tools.py::test_all_tools_excluded_is_refused` (xfail, strict).
- Severity: Medium. Only an unusual input triggers it and no data is lost, but the server fails instead of validating its input, and an app that calls the API gets no message that it can show to the customer.

## Part B
1. Two failures that only a test against the real server finds: (a) faults in how the parts fit together, such as the load balancer sending a login to a server that has never seen the user (Step 0.12), or the real JSON error text that the Go server produces; (b) faults inside the real server code and data, such as the 500 crash when all tools are excluded (Defect 1), which a stub that returns a canned answer would never show. Unit tests with stubs are still worth writing because they are fast, do not depend on the network or on shared data, and point straight to the function that broke, so they can check many edge cases cheaply and never become flaky.
2. A new user with a new name gives each test its own ratings that nobody else can see or change, so the test cannot be disturbed by other students and does not damage data that belongs to everyone. The public token is shared, so its ratings can change at any moment. In Project 2 every test will create its own customer, cart or booking with a unique name (for example with `uuid`), use only that data, and delete it in the fixture after the test, never touching the data of other groups.
3. QuickPizza runs on several servers behind a load balancer, and each server keeps its own users. The `AWSALB` cookie pins a client to one server, and a `requests.Session` keeps that cookie, so the user created by one request and the login in the next request reach the same server. In my three runs of Step 0.12 the first run passed and the other two failed: the user was created (201) but the login answered 401, because it went to a different server. The test is flaky.
4. The block "all three tools excluded" revealed the defect. A 500 with an empty body tells the calling app nothing: it cannot tell a bad input from a server crash, it has no message to show the user, it may retry a request that will always fail, and parsing the empty body as JSON can crash the app too. A 400 with a message says the input is the problem and why. The test stays as `xfail` so the defect stays visible in every run and in the report, the rest of the suite stays green, and with `strict=True` the run tells us as soon as the defect is fixed so the mark can be removed. Deleting the test would hide a known defect.
5. Base choice: 1 base test + (blocks − 1) for each characteristic = 1 + (3−1) + (4−1) + (2−1) + (3−1) = 1 + 2 + 3 + 1 + 2 = 9 tests. All combinations: 3 × 4 × 2 × 3 = 72 tests.
6. I got read 404, change 400 and delete 400. I would expect 403 Forbidden (the user is logged in but may not touch this rating), or 404 for all three if the API wants to hide that the rating exists. Read 404 is acceptable, because it hides the rating. Change and delete answering 400 with "rating ID … not found" are inconsistent: 400 means a bad input, but the input is valid. The security rule holds (the rating is not changed or deleted), so it is not a security defect, but the wrong and inconsistent status codes are a minor defect, because a client cannot tell "you may not" from "your input is malformed".
7. The request with the made-up token `0000000000000000` answers `200` with a long list of ratings (ids 1, 2, 3, …) that were made with other tokens. It is a defect: the API accepts any 16-character token as valid and treats it as a user, while a too-short token gets 401. On a real system a stranger could guess or invent a token and read, and possibly change or delete, data of other users without ever logging in. (I only read with this token.)
8. An API test checks the exact status codes, error messages and every field of the data, including inputs that the web pages never let a user send (such as 0 or 3.5 stars, or a pizza id that does not exist), and it runs faster and more stably. Only a test through the web pages can check what the user actually sees and does: the layout, that buttons and forms work, and that the page shows the data and the error messages correctly.
